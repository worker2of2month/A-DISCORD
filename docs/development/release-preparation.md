# Подготовка обновления A-Discord к релизу

Этот чек-лист нужен для обновлений, которые меняют игровые скрипты, фокусы,
условия доступности или интерфейс. Он разделяет статическую проверку исходников
и доказательство поведения в свежей кампании.

## 1. Зафиксировать исходное состояние

Перед началом работы сохранить вывод:

```powershell
git status --short
git diff --stat
git diff --check
```

Чужие незавершённые изменения не откатывать и не включать в релизный список.
После правок сравнить `git diff --name-only` с этим исходным списком.

## 2. Проверить код и локализацию

Gameplay-файлы (`.txt`) должны быть UTF-8 без BOM. Русская локализация (`.yml`)
должна оставаться UTF-8 с BOM, а значение каждой строки — физически одной
строкой; переносы записываются как `\n\n`.

Для этой ветки достаточно начать с узких тестов:

```powershell
$env:PYTHONIOENCODING = 'utf-8'
python -B -m unittest tools.tests.test_validate_adiscord_val_rework
python -B -m tools.validators.validate_adiscord_val_rework
```

Затем выполнить общий статический проход:

```powershell
$env:PYTHONIOENCODING = 'utf-8'
python -B tools/validate_tc.py --limit 300
git diff --check
```

Если менялся генератор или его выход, сначала запустить dry-run/`--check`,
затем явный `--apply`, после чего ещё раз `--check` и проверить идемпотентность
вторым запуском. Сгенерированные файлы вручную не редактировать.

## 3. Проверить ветку Кефрейта

Статическая проверка должна подтверждать последовательность VAL:

1. `VAL_The_Contract_State` -> `VAL_The_Weaponry_Baron` ->
   `VAL_One_Ledger_One_Banner` открывают базовую систему контрактов.
2. Северные курсы `VAL_Trading_Partners` и `VAL_October_Of_2160`
   взаимоисключающие.
3. `VAL_Contracts_Outlive_Kings` ведёт через `VAL_frontier_conference` к
   логистике, комиссарам и пограничному договору.
4. Хартия и расширение требуют своих условий по регионам, войнам и
   контрактной администрации; новый scripted trigger не должен менять
   результат этих проверок.

При изменении пререквизитов проверять обе северные ветки и послевоенный маршрут.
Обычная дипломатия не является запасным путём: война и союз запускаются только
существующими scripted focus, decision и event-маршрутами.

## 4. Доказать загрузку в игре

Перед запуском записать SHA-256 изменённых загружаемых файлов:

```powershell
$files = @(
  'common/national_focus/ADISCORD_national_focus_VAL.txt',
  'common/scripted_triggers/ADISCORD_VAL_rework_triggers.txt',
  'localisation/english/ADISCORD_VAL_decisions_l_english.yml',
  'localisation/russian/ADISCORD_VAL_decisions_l_russian.yml'
)
$files | ForEach-Object {
  Get-FileHash -Algorithm SHA256 -LiteralPath $_
}
```

Полностью перезапустить Hearts of Iron IV с этими файлами и открыть свежую
кампанию. Проверить не только доступность фокусов, но и реальный переход:

- стартовый гайд показывает порядок базовой, северной и послевоенной веток;
- фокусы экспансии показывают понятные причины блокировки и не открываются
  раньше контроля нужных регионов;
- принятие оружейной сделки не оставляет проданные запасы для своей армии;
- послевоенная администрация и северные решения действительно открываются
  после завершения требуемой кампании;
- в `error.log` нет ошибок загрузки фокусов, scripted triggers, локализации и
  интерфейса.

Статический тест или успешный код валидатора не заменяет эту проверку. После
горячей перезагрузки открытого события результат не считать доказательством:
нужен полный перезапуск и новая кампания.

## 5. Сформировать релизный набор

Перед публикацией выполнить:

```powershell
git diff --name-only
git diff --stat
git diff --check
```

В список должны попасть только проверенные исходники, локализация и нужные
ассеты. Локальную копию `A-Discord-release` обновлять и сверять по SHA-256
только после отдельного разрешения на копирование; Workshop не является
источником проверки. Для каждой скопированной пары файл должен иметь одинаковый
хеш, а итоговый список файлов — совпадать с проверенным `git diff`.

В итоговой записи релиза сохранить:

- commit или архивный идентификатор исходников;
- список изменённых файлов и их SHA-256;
- результаты узких тестов и `validate_tc.py`;
- дату свежего запуска и краткий результат кампании;
- известные ограничения, которые статикой не доказываются.

Если любой пункт runtime-проверки не выполнен, обновление считать готовым к
внутреннему тесту, но не к публичному релизу.
